## 2. パッケージ構成（機能単位）

レイヤード構成（controller/service/repositoryを最上位で分割）ではなく、**機能（Feature）単位**でパッケージを分割する。1機能追加・変更時に触るファイルが1パッケージに閉じることを優先する。

```text
com.ieltscreator.api
├── common/                  # 横断的関心事（どの機能にも属さないもの）
│   ├── config/              # Security, Cors, Async(Virtual Threads), RestClient, OpenAI/Polly/S3クライアントBean
│   ├── exception/           # カスタム例外, GlobalExceptionHandler（@RestControllerAdvice）
│   ├── security/            # Cognito JWT検証カスタマイズ（CognitoJwtValidatorConfig等）
│   └── web/                 # 共通DTO（ErrorResponse等）, ページングDTO
│
├── user/                    # ユーザー機能（F-01関連）
│   ├── MeController
│   ├── UserProvisioningService
│   ├── AppUser                # JPAエンティティ
│   ├── AppUserRepository
│   └── dto/                   # MeResponse等
│
├── questionset/              # 問題生成機能（F-02〜F-06, F-12）
│   ├── QuestionSetController
│   ├── QuestionSetGenerationService  # topic未指定時はプリセットからランダム選択
│   ├── generation/            # ReadingQuestionGenerator, ListeningQuestionGenerator（OpenAI連携）
│   ├── listening/             # ListeningAudioSynthesizer, StorageService(interface),
│   │                          # LocalDiskStorageService（Phase1）, S3StorageService（Phase3）
│   ├── QuestionSet / Passage / ListeningScript / AudioSegment /
│   │   QuestionGroup / Question / AnswerOption / AcceptableAnswer   # JPAエンティティ
│   ├── (各エンティティに対応するRepository)
│   └── dto/                    # QuestionSetCreateRequest, QuestionSetResponse等
│
├── attempt/                   # 受験・採点機能（F-07〜F-10）
│   ├── AttemptController
│   ├── AttemptSubmissionService
│   ├── grading/                # AnswerGrader(interface), TfngGrader, McqGrader,
│   │                           # FillBlankGrader, MatchingHeadingsGrader, GraderFactory
│   ├── Attempt / AttemptAnswer  # JPAエンティティ
│   ├── AttemptRepository / AttemptAnswerRepository
│   └── dto/                     # AttemptStartRequest, AttemptResultResponse等
│
└── dashboard/                  # ダッシュボード機能（F-11）
    ├── DashboardController
    ├── DashboardSummaryService
    ├── DashboardQueryRepository   # attempt/questionsetを横断する集計専用クエリ
    └── dto/                       # DashboardSummaryResponse等
```

### 2.1 機能パッケージ間の依存ルール

- 参照は一方向を基本とする: `attempt → questionset`, `attempt/questionset → user` は許可。逆方向（`questionset → attempt`等）は禁止
- `dashboard`は`attempt`/`questionset`のRepositoryを読み取り専用で参照してよい（集計はJOINクエリまたは複数リポジトリの組み合わせで実装し、`dashboard`独自のJPAエンティティは持たない）
- 他機能のエンティティへの参照は、外部キーの列で問題ない箇所（例: `Attempt.questionSetId`）は`UUID`型のIDで保持し、必要な場合のみ`@ManyToOne`を許可する（N+1回避のため一覧系クエリでは`@EntityGraph`または専用クエリを使う）
- 機能をまたぐ共通処理（例外・セキュリティ・外部クライアントBean）は`common/`に置く。`common/`から各機能パッケージへの依存は禁止（逆方向のみ）

### 2.2 命名規約

| 種別 | 命名 | 例 |
| --- | --- | --- |
| Controller | `{機能}Controller` | `QuestionSetController` |
| Service | `{責務}Service` | `AttemptSubmissionService` |
| Repository | `{Entity}Repository`（Spring Data JPA） | `QuestionSetRepository` |
| JPAエンティティ | ER図・テーブル定義.mdのテーブル名をUpperCamelCase化（Entityサフィックスは付けない） | `question_set` → `QuestionSet` |
| リクエストDTO | `{対象}{操作}Request` | `QuestionSetCreateRequest` |
| レスポンスDTO | `{対象}Response` | `QuestionSetResponse` |
| カスタム例外 | `{内容}Exception` | `ResourceNotFoundException` |
| Config | `{対象}Config` | `SecurityConfig` |

## 3. コーディングスタイル

### 3.1 Lombok

- JPAエンティティ: `@Getter` `@Setter` `@NoArgsConstructor`（JPA要件） `@Builder` + `@AllArgsConstructor(access = AccessLevel.PRIVATE)`（Builder用）を基本とする
- `@Data`は使わない（`equals`/`hashCode`がJPAエンティティで問題を起こしやすいため）。エンティティで`equals`/`hashCode`が必要な場合はID（サロゲートキー）のみを対象に手動実装する
- Service層は`@RequiredArgsConstructor` + `final`フィールドでコンストラクタインジェクションを基本とする（フィールドインジェクション禁止）

### 3.2 DTO

- リクエスト/レスポンスDTOは**Java record**を基本とする（Lombokは使わずシンプルに保つ）
- リクエストDTOには`jakarta.validation`のアノテーション（`@NotNull` `@NotBlank` `@Size`等）を付与し、Controllerでは`@Valid`で検証する
- Entity→DTO変換は各機能パッケージ内に`{Entity}Mapper`（静的メソッドまたは軽量なコンポーネント）を用意し、MapStruct等の外部ライブラリは導入しない（変換ロジックが複雑化してきた時点で再検討）

### 3.3 例外処理

[API一覧.md 2.1 例外とHTTPステータスの対応](./API一覧.md#21-例外とhttpステータスの対応)で定義した対応表に従う。カスタム例外は`common/exception/`に置き、`GlobalExceptionHandler`（`@RestControllerAdvice`）で一元的にエラーレスポンスへ変換する。各Controller/Serviceで個別にtry-catchしてレスポンスを組み立てない。

### 3.4 外部API連携（HTTPクライアント・AWS SDK）

外部API呼び出しは認証方式によって使い分ける。Virtual Threads前提のため、いずれも`WebClient`（リアクティブ）や非同期化のための独自スレッドプールは導入しない。

- **OpenAI**（APIキーによるプレーンHTTP認証）: Spring Boot 3.2+の`RestClient`（同期）を使用する
- **Polly / S3**（AWS SigV4署名が必要）: AWS SDK for Java v2（`software.amazon.awssdk:*`）の同期クライアントを使用する。SigV4署名を手動実装するとリスク・保守コストが高いため、公式SDKに委ねる

#### リトライ・タイムアウト設定値（R-3、#00033で確定）

問題生成の内容面（ルールベース検証）に対する1回リトライ（[3章 生成〜永続化の処理フロー](./API設計書/POST_question-sets.md)参照）とは別に、外部API呼び出し自体（ネットワーク層）に対して以下の設定を行う。

| 対象 | 接続/呼び出しタイムアウト | 応答待ちタイムアウト | 最大試行回数 | リトライ方式 |
| --- | --- | --- | --- | --- |
| OpenAI（`RestClient`） | 5秒 | 60秒 | 2回（初回+1回） | 生成器クラス内で手組み。5xx/429等の一時的エラーのみ対象、4xxは即失敗。バックオフ2秒 |
| Polly（AWS SDK） | `apiCallAttemptTimeout` 10秒 | `apiCallTimeout` 25秒 | 3回 | AWS SDK v2組み込みの`RetryStrategy`に委ね、独自実装は行わない |

いずれも試行を使い切った後は例外をそのまま呼び出し元へ伝播させる。問題生成オーケストレーション側（`QuestionSetGenerationWorker`）の「ルール検証1回リトライ・`status=FAILED`・ユーザーごと1日2回のレート制限」ロジックは変更しない。設定値は`app.openai.*` / `app.polly.*`（`application.yml`）で調整可能にする。

## 4. DBマイグレーション（Flyway）

- マイグレーションファイルは`src/main/resources/db/migration/`配下に`V{連番}__{説明（英語・snake_case）}.sql`で配置する（例: `V1__create_app_user_table.sql`）
- `spring.jpa.hibernate.ddl-auto`は`validate`固定とし、スキーマ変更は必ずマイグレーションファイル経由で行う（エンティティ変更とマイグレーション追加は同一PRで行う）
- 一度リリースした（`develop`にマージ済みの）マイグレーションファイルは変更しない。修正が必要な場合は新しいバージョンファイルを追加する
- テーブル定義は[ER図・テーブル定義.md](./ER図・テーブル定義.md)を正とし、マイグレーション追加時は当該ドキュメントも合わせて更新する

## 5. テスト方針

### 5.1 種別

| 種別 | 対象 | 手法 |
| --- | --- | --- |
| Unit Test | Service/Grading/Mapperの単体ロジック | JUnit 5 + Mockito（依存はモック化） |
| Integration Test | Repository, Controller（Web層〜DB） | JUnit 5 + `@SpringBootTest` + Testcontainers（実PostgreSQLコンテナ） |

- 配置は`src/test/java`配下に`main`と同じ機能パッケージ構成でミラーリングする
- クラス名: Unit Testは`{対象クラス}Test`、Integration Testは`{対象クラス}IntegrationTest`
- Integration Testには`@Tag("integration")`を付与する。Gradle側で以下のようにタスクを分離する:
  - `test`タスク: `excludeTags "integration"`（高速なUnit Testのみ、PRの通常チェック）
  - `integrationTest`タスク（カスタムタスク）: `includeTags "integration"`（Testcontainers利用、Docker必須）
- 外部API（OpenAI/Polly）は原則モック化し、実APIへの呼び出しはテストで行わない（コスト・再現性の観点）

## 6. ロギング

[API一覧.md 4章 ロギング方針](./API一覧.md#4-ロギング方針)で定義した必須フィールド（`timestamp`, `level`, `traceId`, `userId`, `message`）を満たすため、以下を実装する。

- `logstash-logback-encoder`によるJSON形式のログ出力（`logback-spring.xml`）
- `traceId`はServletフィルタで採番しMDCに格納する（将来的にAWS X-Ray等に移行する場合も同フィルタを差し替えるだけで済む構成とする）
- `userId`はCognito JWT検証後にMDCへ格納する（未認証エンドポイントでは省略）
- ログ出力箇所（OpenAI/Polly呼び出し、生成バリデーション、採点確定、認証エラー）は各機能パッケージ内のService/Controllerに実装し、共通のログユーティリティは持たない（過度な抽象化を避ける）

## 7. 設定・プロファイル

- `application.yml`: 全環境共通の設定（`spring.threads.virtual.enabled: true`、Flyway有効化等）
- `application-local.yml`: ローカル開発用（`docker-compose.yml`で起動するPostgres接続情報、ダミーのAPIキー、`StorageService`は`LocalDiskStorageService`を使用）
- `application-prod.yml`: Phase3以降の本番向け設定。DBはSupabase（マネージドPostgreSQL、`sslmode=require`必須）、それ以外はAWS（S3/Polly/Cognito）を利用する。認証情報・接続文字列はSecrets Manager経由の環境変数で注入し、ファイルには書かない（[ielts-creater #00037](https://github.com/h-fujiwara-dev/ielts-creater/blob/main/tickets/00037_インフラ構成の見直し（Vercel_Supabase化）とREADME構成図の追加.md)）
- Phase1（認証なし・固定devユーザー）とPhase2以降（Cognito認証あり）の切り替えは、`app.auth.mode`プロパティ（`no-auth` / `cognito`）と`@ConditionalOnProperty`によるBean切り替えで行う（`NoAuthSecurityConfig`/`NoAuthCurrentUserProvider` と `CognitoSecurityConfig`/`CognitoCurrentUserProvider` が排他的に有効化される。#00034で確定）
- stub実装と実装（OpenAI/Polly連携）の切り替えは`app.generation.mode`（`stub`|`openai`）で行う（#00033）。`app.auth.mode`と同じ`@ConditionalOnProperty`方式だが、`app.auth.mode`とは逆に**`stub`を全環境共通の既定値**とする（`application.yml`に明示、未設定時も`matchIfMissing=true`でstubにフォールバック）。結合テスト（`AbstractIntegrationTest`）はlocalプロファイルを有効化しないため、既定をstub以外にすると外部APIへの実呼び出しが発生してしまうことによる。実際にOpenAI/Pollyへ接続する場合のみ環境変数`APP_GENERATION_MODE=openai`で上書きする（Phase3で本番運用が固まった時点で`application-prod.yml`側の既定値化を検討する）

## 8. 非同期・Virtual Threads方針

- `spring.threads.virtual.enabled: true`によりTomcatのリクエスト処理スレッドをVirtual Threadsで動作させる
- OpenAI/Polly呼び出しのような外部I/O待ちは、Virtual Threadsが自動的にプラットフォームスレッドを解放するため、`@Async`や独自スレッドプールを使わず同期コードのまま実装してよい
- 問題生成はAPIレスポンス自体は202 Acceptedで即時返す（[API一覧.md](./API一覧.md#1-api一覧)参照）。バックグラウンド実行は`@Async`ではなく、リクエストスレッド内でVirtual Threadを使った同期呼び出し＋別スレッドへの委譲（`ExecutorService`にVirtual Thread Executorを使う）で実装する方針とし、実装時のクラス設計はチケットで確定する
